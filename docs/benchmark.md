# 性能基准（vfs_bench）

`bench/vfs_bench.cpp` 是一个不依赖第三方库的基准程序，对比直接调用 C / C++ / OS 文件 API 的基线与各种 VFS 后端、分层组合在读、写、元数据操作上的吞吐和延迟。

## 构建与运行

默认不构建，用 `VFS_BUILD_BENCH` 打开。务必使用 Release 构建，Debug 下的数字没有参考价值（程序启动时会提示构建类型）。

```bash
cmake -S . -B build-bench -DCMAKE_BUILD_TYPE=Release -DVFS_BUILD_BENCH=ON -DVFS_BUILD_TESTS=OFF
cmake --build build-bench --target vfs_bench -j
./build-bench/bench/vfs_bench                                  # 全部场景，线程 1,2,4,8,N，热缓存
./build-bench/bench/vfs_bench --filter read.small,archive-lz4  # 只跑名字含任一子串的 "场景/目标"
./build-bench/bench/vfs_bench --scale 0.1 --threads 1,4 --iterations 1   # 快速冒烟
./build-bench/bench/vfs_bench --csv out.csv --md out.md        # 额外输出 CSV / Markdown
./build-bench/bench/vfs_bench --cold --threads 1,8 --filter read.   # 冷缓存（仅 Linux）
```

Windows（MSVC）下用 `cmake --build build-bench --config Release`，可执行文件在 `build-bench/bench/Release/vfs_bench.exe`。

| 选项 | 说明 |
|---|---|
| `--scale <x>` | 数据规模倍数，默认 1：小文件 10000 个 × 4 KiB（放在同一个目录里）、中文件 200 个 × 256 KiB、大文件 64 MiB；随机读次数、写入文件数同比缩放 |
| `--threads <list>` | 线程数列表，`N` 表示硬件线程数，默认 `1,2,4,8,N`（重复的自动去掉） |
| `--iterations <n>` | 每个组合重复次数，取耗时中位数的那一次，默认 3 |
| `--filter <list>` | 逗号分隔的子串，匹配 `场景/目标`，任一命中即运行 |
| `--csv <file>` / `--md <file>` | 额外输出 CSV / Markdown 表格 |
| `--dir <path>` | 工作目录，默认系统临时目录；数据集约 0.5 GB（scale=1：原始文件 154 MiB + 三个归档） |
| `--keep` | 结束后保留数据集 |
| `--cold` | 每次迭代前用 `posix_fadvise(DONTNEED)` 把数据文件逐出页缓存（仅 Linux，不需要 root）；默认先预跑一次再计时（热缓存） |
| `--list` | 列出场景与目标 |

### 场景

每个线程做同样多的工作（弱扩展），总吞吐 = 全部线程的操作数 ÷ 墙钟时间。

| 场景 | 一次操作 |
|---|---|
| `read.small` | 打开 + 读完 4 KiB + 关闭；每个线程读全部小文件，起点错开 |
| `read.medium` | 打开 + 以 64 KiB 分块读完 256 KiB + 关闭 |
| `read.large.seq` | 以 1 MiB 分块顺序读完 64 MiB 大文件，每线程一遍；延迟按块统计 |
| `read.large.rand` | 大文件打开一次，随机偏移读 4 KiB（seek + read，基线 posix 用 `pread`）；打开计入总时间但不计入单次延迟 |
| `meta.open` | 只打开再关闭小文件 |
| `meta.stat` | `stat` 已存在的小文件 |
| `meta.miss` | `exists` 查询大目录中不存在的名字 |
| `meta.list` | 列出含 10000 个文件的目录，每线程 10 次 |
| `write.create` | 每个线程在自己的目录里新建并写入 64 KiB 文件 |
| `write.churn` | 新建写入 4 KiB 文件再删除（一次操作 = 创建 + 删除） |

### 目标

| 目标 | 说明 |
|---|---|
| `base:stdio` | `fopen` / `fread` / `fseeko`；**比值的基准**。`meta.stat`/`miss`/`list` 用 `std::filesystem`（status / exists / directory_iterator） |
| `base:fstream` | `std::ifstream` / `std::ofstream` |
| `base:posix` / `base:win32` | POSIX `open`/`read`/`pread`；Windows 上是 `CreateFileW`/`ReadFile`（带 OVERLAPPED 偏移） |
| `vfs:native` | `NativeBackend` 单独挂载 |
| `vfs:memory` | `MemoryBackend`，预先装入全部数据 |
| `vfs:archive` / `-xor` / `-lz4` | 同一数据集打成的三个归档：明文、全部 XOR 加密、全部 LZ4 压缩（42 MiB，约 3.7:1） |
| `vfs:archive+native` | 归档在下 + 空的本机覆盖目录在上（开发期“本机文件覆盖归档”的用法），同一挂载点 |
| `vfs:memory+archive` | 归档在下 + 空的可写内存层在上 |
| `vfs:3layer` | 归档 + 本机覆盖 + 内存（WriteTarget）三层 |
| `vfs:nested8` | 数据目录挂在 8 级深的路径上，每一级祖先都有一个空的内存挂载（查找要经过 9 层），另有 32 个无关挂载 |

写场景的目标是三个基线、`vfs:native`、`vfs:memory`、`vfs:memory+archive`（写入落到内存层，父目录由 VFS 在写入层创建）。

### 指标

- `ops/s`：操作数 ÷ 墙钟时间；`MiB/s`：读写字节数 ÷ 墙钟时间（元数据场景为 `-`）。
- `p50` / `p99`：所有线程合并后的单次操作延迟（微秒）。
- `vs stdio`：同一场景、同一线程数下吞吐相对 `base:stdio` 的倍数，> 1 表示比 stdio 快。

### 热缓存与冷缓存

- 默认是**热缓存**：先预跑一次，数据都在页缓存里，测到的是 API 与 VFS 本身的开销（系统调用、查找、拷贝、解密、解压）。游戏运行时反复读同一批资源时更接近这种情况。
- `--cold` 在每次迭代前逐出数据文件的页缓存，测到的是首次加载的情况，结果主要取决于存储设备与预读。目录项 / inode 缓存不会被清除（需要 root），所以 `meta.*` 场景在冷缓存下差别不大。macOS / Windows 上 `--cold` 不起作用（可以用重启或 `purge`（macOS）代替）。
- 虚拟机磁盘通常还有一层宿主机缓存，冷缓存数字会比真机的 SSD/HDD 乐观。

## 本机结果

- 日期：2026-10-16（UTC+8）
- 机器：KVM 虚拟机，Intel Xeon（8 vCPU，每核 1 线程），15 GiB 内存，virtio 磁盘，ext4
- 系统：Debian 13（trixie），Linux 6.12
- 编译器：GCC 14.2.0，`-O3 -DNDEBUG`（CMake Release），CMake 3.31

- 共享虚拟机上的数字有 ±20% 左右的波动，比较时看数量级和趋势，不要看小数点。

## 分析

### VFS 的开销从哪里来

1. **路径处理与挂载表查找**：每次调用都要规范化路径（分配一个 `std::string`）、取一次挂载表快照（`m_mutex` 加锁 + `shared_ptr` 引用计数增减），再按挂载点前缀收集层栈（`std::vector<Layer>`）。单线程下这部分只有几百纳秒：`vfs:archive` 的 `meta.stat` 是 0.19 µs，比 `std::filesystem::status`（1.2 µs，一次 `stat` 系统调用）还快 5 倍。
2. **逐层查找**：读操作自上而下逐层 `stat`，直到命中。空的上层也要查一次：`archive+native` 的上层是本机目录，每次查找多一次 `stat` 系统调用，所以 `meta.stat` 从 3.9 M/s 降到 1.5 M/s，`meta.miss` 降到与 stdio 持平；内存层的查找只是一次哈希表 / 树查找，`memory+archive` 几乎没有损失。`nested8` 要查 9 层（8 个空内存层 + 本机），`meta.*` 只有直接调用的 0.5 ~ 0.8 倍。
3. **列目录**：VFS 要汇总所有层、按名字去重并排序（`std::map`），对本机目录还要判断每一项的类型并转换文件名，所以 `vfs:native` 列 10000 项的目录比 `directory_iterator` 慢约 1.5 倍（4.3 ms 对 2.7 ms）。归档的目录列表直接来自内存索引，反而快 2.5 ~ 3.7 倍。
4. **流包装**：VFS 返回的流在后端流外再包一层（统计打开数量、保活后端），每次 `read` 多一次虚函数调用，热缓存下读 4 KiB 文件的成本主要还是 `open`/`close` 系统调用，`vfs:native` 与 stdio 基本持平（0.94 ~ 1.3 倍）。
5. **XOR 解密**：按字节异或，热缓存下单线程顺序读从 5269 MiB/s 降到 4628 MiB/s，8 线程时成为瓶颈（85542 → 58211 MiB/s，约 0.6 倍）。
6. **LZ4 压缩条目**：压缩条目不能按偏移读取，`open` 时整体解压到内存。小文件（4 KiB）影响不大；256 KiB 文件约 0.4 ~ 0.6 倍；64 MiB 大文件第一次读要等解压完（第一个块的 p99 ≈ 56 ms），顺序读只有 stdio 的 0.07 ~ 0.16 倍，随机读更差（每个线程都要先解压整个文件）。**大文件不要用 LZ4，或者只压缩脚本、配置等小文件**（`vfstool pack --compress "*.lua"`）。
7. **归档的读取路径**：未压缩条目每次 `open` 打开一个新的 OS 句柄，读时按需 seek，与直接读文件几乎一样；但多了一层 `ArchiveFileStream → NativeFileStream` 的转发，热缓存下大文件顺序读约 0.85 倍。

### 哪些组合更慢，为什么

- **LZ4 归档读大文件**：最慢（0.07 ~ 0.16 倍），原因见上，是“整体解压”的设计取舍。
- **多线程元数据（`meta.stat` / `meta.miss`）**：VFS 在 1 线程时比 stdio 快，但几乎**不随线程数扩展**：各种组合在 2 ~ 8 线程都停在 2 ~ 3 M/s，而 `stat` 系统调用能扩展到 3.4 ~ 7 M/s，8 线程时 VFS 只有 0.3 ~ 0.8 倍。瓶颈是每次调用都要取挂载表快照：同一把 `m_mutex` 和同一个 `shared_ptr` 控制块的引用计数被所有线程争用（缓存行在核间来回）。如果游戏在多个线程上高频做 `exists`/`stat`，这是最值得优化的地方（例如改成按线程缓存快照、只在挂载表版本号变化时刷新，或用 hazard pointer / RCU 取代引用计数）。`meta.open` 与读文件的场景每次操作本身更重，这部分开销被摊薄，8 线程时仍有 1.1 ~ 1.3 倍。
- **深层嵌套（nested8）**：查找经过 9 层，元数据操作 0.4 ~ 0.8 倍、`read.small` 0.7 倍（1 线程）；读大文件不受影响。挂载点的数量本身影响不大（另外 32 个无关挂载只增加前缀比较），影响大的是**同一路径上叠了多少层**。
- **本机覆盖层（archive+native、3layer）**：上层每多一个本机目录，每次查找多一次 `stat` 系统调用；发布版本里如果不需要本机覆盖，就不要挂空的本机目录。
- **内存后端的并发写**：`MemoryBackend` 的目录树由一把读写锁保护，创建 / 删除需要独占锁。单线程比本机快 4 ~ 5 倍，但 `write.churn` 在 2 线程以上反而下降（8 线程 0.43 倍）。`write.create` 的数据拷贝在锁外，影响小一些。
- **本机后端的创建 / 删除**：`vfs:native` 的 `write.churn` 约 0.6 ~ 0.8 倍：VFS 在写之前要确定写入层、检查父目录（多一次 `stat`），删除时也要先查可见项。

### 哪些组合更快

- **内存后端**：没有系统调用，读、`stat`、写都快 2 ~ 5 倍；冷缓存下差距更大（不受磁盘影响）。
- **归档读大量小文件**：热缓存下 1.2 ~ 1.4 倍（打开时不走目录查找与权限检查，`stat` 查的是内存索引）。**冷缓存下 4.7 ~ 6 倍**：小文件在归档里连续存放，内核预读一次就能带进很多文件，而散落的小文件每个都要单独读盘。这是打包资源最直接的收益。
- **归档的元数据与列目录**：全部来自内存索引，单线程 `stat` 约 5 倍、列目录约 2.5 ~ 3.7 倍。

### 结论

- 发布版本推荐“明文或 XOR 归档 + 可写内存 / 本机层”的两层结构；只压缩小的文本类文件。
- 避免在同一挂载点上叠加不必要的空层，尤其是本机目录。
- 热缓存下，VFS 读文件的开销与直接调用 C API 在同一量级（0.85 ~ 1.4 倍）；多线程高频 `stat` 是目前唯一明显的扩展性短板。
